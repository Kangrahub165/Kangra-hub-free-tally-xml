# Product Requirements Document (PRD)

## Suspended Account Login, Administrator Contact & Appeal System

### Product

Kangra Hub – Free Tally XML

### Objective

Fix the current security issue where a user can still log in even after an administrator has suspended the user's account.

When an administrator suspends a user account:

1. The user MUST NOT be allowed to access the authenticated application.
2. The user MAY enter their email/password on the login page, but authentication must immediately check the account status.
3. If the account is suspended, the user must be shown a professional suspended-account UI instead of being logged into the application.
4. The suspended user must have an option to contact the administrator and submit an appeal/review request.
5. The submitted request must appear inside the Admin Dashboard.
6. The administrator must be able to review the user's account and decide whether to recover the account or keep it suspended.
7. The user must receive an email notification whenever the account is recovered or remains suspended after an appeal/review.
8. If the account remains suspended, the user must be informed that the account is scheduled for deletion after 3 months from the suspension date, unless the administrator recovers it before deletion.

# 2. ACCOUNT STATUS SYSTEM

The application must have a reliable account-status check.

At minimum, support:

* `active`
* `suspended`

If the existing database already has an equivalent status field, reuse it instead of creating a duplicate field.

Recommended additional fields if they do not already exist:

```text
account_status
suspended_at
suspension_reason
suspension_delete_at
suspension_reviewed_at
suspension_reviewed_by
```

### Suspension date

When an administrator suspends an account:

```text
suspended_at = current timestamp
```

### Scheduled deletion date

Automatically calculate:

```text
suspension_delete_at = suspended_at + 3 months
```

The account must NOT automatically be deleted merely because the date has been reached unless the existing product requirements already specify an automated deletion process.

Instead, the system must clearly mark/show that the account is eligible for deletion after 3 months.

If automatic deletion is implemented, it must be safe and must not accidentally delete active/recovered accounts.

# 3. LOGIN SECURITY – CRITICAL

This is the most important requirement.

Currently, a suspended user can still log in.

FIX THIS.

After successful authentication, immediately check the user's account status before allowing access to any protected application route.

Required flow:

```text
User enters email/password
        ↓
Authentication
        ↓
Fetch account status
        ↓
Is account suspended?
        ↓
YES
        ↓
Do NOT allow access to application
        ↓
Show Suspended Account Screen
```

A suspended user must never be able to access:

* User Dashboard
* PDF upload
* Conversion
* Ledger management
* Excel export
* Tally XML export
* Account settings
* Any other authenticated application route/API

Do not rely only on frontend route protection.

The backend/API must also validate account status for protected operations.

A user must not be able to bypass suspension by:

* Directly opening a dashboard URL
* Refreshing the page
* Using an old session
* Using an existing access token
* Calling protected APIs directly
* Opening an old browser tab
* Manipulating frontend state

---

# 4. SESSION HANDLING

When an administrator suspends a user who is currently logged in:

The user's existing session must become invalid for protected application functionality.

On the next API request/session validation:

```text
account_status = suspended
```

must cause access to be denied.

The frontend should redirect the user to the suspended-account screen.

Do not allow a previously logged-in suspended user to continue using the application.

# 10. SUPABASE / DATABASE SECURITY

This feature must follow the application's existing RLS/security architecture.

Users must only be able to:

* Create their own appeal
* View their own submitted appeals, if appeal history is exposed to them

Users MUST NOT be able to:

* View another user's appeal
* Modify another user's appeal
* Change appeal status
* Approve their own appeal
* Recover their own account through client-side manipulation

Only authorized administrators can:

* View all appeals
* Review appeals
* Change appeal status
* Recover accounts
* Keep accounts suspended
* Add administrator responses

Do not solve this by exposing service-role keys in frontend code.

# 13. ADMIN DECISION – RECOVER ACCOUNT

**Recover Account**

> Are you sure you want to recover this account?

After confirmation:

```text

```

Also:

```text

suspension_reason = null
suspension_delete_at = null
```

Preserve the user's existing account data.

Do NOT delete:

* User history
* Conversion history
* Existing files/data
* User settings
* Other legitimate account data

unless the existing application explicitly requires it.

Update the appeal:

```text
status = approved
reviewed_at = current timestamp
reviewed_by = current admin
```

# 21. ACCOUNT DELETION – 3 MONTH RULE

When an account is suspended:

```text
suspension_delete_at = suspension date + 3 months
```

The UI and emails must communicate this clearly.

If the account is recovered before the deletion date:

```text
account_status = active
suspension_delete_at = null
```

The account must NOT be deleted.

If the account remains suspended after the deletion eligibility date, it should be clearly flagged in Admin Dashboard as:

**Eligible for Deletion**

Do not implement irreversible automatic deletion unless explicitly supported by the current application's data-retention requirements and administrator controls.

If automatic deletion is implemented, create a safe scheduled backend job that:

1. Checks account status.
2. Checks the exact deletion date.
3. Confirms the account is still suspended.
4. Does NOT delete recovered accounts.
5. Records the deletion event.
6. Handles related user data according to the application's existing retention policy.

# 22. BACKEND API PROTECTION

Every protected backend endpoint must reject suspended users.

Do not only protect the frontend.

Example conceptual middleware:

```text
authenticate user
       ↓
load account status
       ↓
if account_status == suspended
       ↓
return 403 ACCOUNT_SUSPENDED
```

Response should contain a machine-readable code:

```json
{
  "error": "ACCOUNT_SUSPENDED",
  "message": "Your account has been suspended."
}
```

The frontend must detect this response and redirect/show the suspended-account UI.

# 26. TESTING REQUIREMENTS

Before considering this feature complete, test the following scenarios.

### Test 1 – Active user

```text
Active user → Login → Dashboard
```

Expected: Works normally.

### Test 2 – Suspended user

```text
Suspended user → Login
```

Expected:

* Login access denied
* Dashboard inaccessible
* Suspended-account UI shown

### Test 3 – Direct URL

```text
Suspended user → /dashboard
```

Expected:

* User cannot access dashboard
* Redirect to suspended-account screen

### Test 4 – API bypass

Attempt protected API requests using a suspended user's session/token.

Expected:

```text
403 ACCOUNT_SUSPENDED
```

### Test 5 – Appeal

Suspended user submits appeal.

Expected:

* Appeal stored
* Confirmation displayed
* Appeal appears in Admin Dashboard

### Test 6 – Admin recovery

Admin approves appeal/recover account.

Expected:

* User status becomes active
* Appeal becomes approved
* Suspension fields cleared appropriately
* Recovery email sent
* User can log in normally

### Test 7 – Admin rejection

Admin keeps account suspended.

Expected:

* User remains suspended
* Appeal becomes rejected
* Administrator response is stored
* Suspension/review email sent
* Scheduled deletion date remains visible

### Test 8 – Existing session

User logs in while active.

Admin then suspends the user.

Expected:

* Existing session cannot continue using protected application features.
* Next protected API/session check detects suspension.
* User is redirected to suspended-account UI.

### Test 9 – Recovered account

Admin recovers a previously suspended account.

Expected:

* User can log in normally
* Old suspension warning is not shown
* Account is no longer marked for deletion

### Test 10 – Duplicate appeals

User rapidly clicks Submit multiple times.

Expected:

* No duplicate appeals are created.
